## 3. Критерии проверки (чек-лист)

Конкретные, измеримые вопросы, на которые должны ответить рецензенты.

### 3.1. Функциональная корректность

- [ ] Корректно ли реализованы все основные сценарии: успешный логин, неуспешный логин, прохождение 2FA, обновление/инвалидация сессионных токенов?
- [ ] Правильно ли обрабатываются граничные случаи (пустые поля, слишком длинные пароли/логины, повторная отправка 2FA-кода, истёкший токен)?
- [ ] Есть ли unit- и integration-тесты на happy-path и основные негативные сценарии? Покрывают ли они критические ветки?
- [ ] Корректно ли работает выход из системы (logout) с полной инвалидацией сессии на сервере?
- [ ] Соответствует ли поведение модуля ожидаемым бизнес-требованиям банка (таймауты сессий, политики паролей)?

### 3.2. Безопасность

- [ ] Пароли хешируются с использованием сильного алгоритма (Argon2 / PBKDF2 / bcrypt)? Нет ли использования устаревших хешей (MD5, SHA-1)?
- [ ] Сравнение паролей выполняется константным по времени (constant-time)?
- [ ] Реализована защита от brute-force (rate limiting / блокировка аккаунта после N неудачных попыток)?
- [ ] Сессионные токены/куки имеют флаги Secure, HttpOnly, SameSite=Lax/Strict? Токен сессии регенерируется после успешного логина?
- [ ] 2FA реализована безопасно (одноразовые коды с ограниченным временем жизни, защита от повторного использования)?
- [ ] Нет логирования паролей, 2FA-кодов, полных токенов или чувствительных персональных данных?
- [ ] Соблюдаются требования 152-ФЗ: минимизация обрабатываемых ПДн, согласие пользователя, шифрование чувствительных данных при хранении/передаче, аудит доступа?
- [ ] Отсутствуют hardcoded secrets (SECRET_KEY, ключи API и т.д.)? Секреты берутся из переменных окружения / secrets manager?
- [ ] Используются только параметризованные запросы (ORM Django)? Нет raw SQL с пользовательским вводом?
- [ ] CSRF-защита включена и корректно применяется ко всем изменяющим запросам?
- [ ] Нет уязвимостей типа IDOR, privilege escalation или доверия к данным с клиента (роли, ID пользователя)?

### 3.3. Производительность

- [ ] Операции авторизации (логин + 2FA) выполняются за приемлемое время (< 1-2 секунд при нормальной нагрузке)?
- [ ] Нет лишних запросов к БД в критическом пути (N+1 проблемы)?
- [ ] Правильно ли используются кэширование сессий / rate-limit counters?
- [ ] При высокой нагрузке (много одновременных логинов) модуль не создаёт bottlenecks?

### 3.4. Читаемость и стиль

- [ ] Код соответствует PEP 8 и принятому в команде стилю (black / isort / flake8)?
- [ ] Названия переменных, функций и классов понятны и отражают суть (особенно в security-критичных местах)?
- [ ] Сложная логика (2FA, управление токенами) сопровождается комментариями «почему», а не «что»?
- [ ] Нет дублирования кода? Выделены ли переиспользуемые компоненты (валидаторы, сервисы)?
- [ ] Документация (docstrings, README модуля) актуальна и достаточна для поддержки другими разработчиками?
